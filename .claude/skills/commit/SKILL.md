# commit

Stage and commit the current changes with a useful message.

## Workflow

1. `git status` to see modified/untracked files.
2. `git diff --stat` and `git diff` (or `git diff --cached` if anything's staged) to understand the change.
3. Decide what to stage:
   - If the user named specific files, stage those.
   - Otherwise, stage every tracked modified file plus untracked-but-clearly-intentional new files.
   - NEVER stage with `git add -A` or `git add .` blindly — it can sweep secrets or stray files.
4. If the project has a fast lint/test gate configured in CLAUDE.md, run it. Fix obvious issues before committing. If the gate is slow, skip and note it.
5. Compose the commit message:
   - Subject: ≤72 chars, imperative ("add X", "fix Y"), no period.
   - Body: 1-2 lines on the WHY. Skip if the subject is self-explanatory.
   - No "Generated by Claude" footers unless `includeCoAuthoredBy` is true.
6. `git commit -m "$(cat <<'EOF'\n<message>\nEOF\n)"` so multi-line messages format correctly.
7. `git status` to confirm.

## Constraints

- Refuses if the current branch matches the protected-branch list in `.claude/.meta/protected-branches.json`. In that case, tell the user to switch branches or pass `--force-on-protected` (which means asking again with a `commit on protected branch:` prefix).
- Doesn't push. Pushing is the `open-pr` skill's job (when +pr-flow is installed) or an explicit user action.
- Doesn't run installs — if the lint/test gate needs deps, surface that to the user instead of `npm install`-ing.

## After the commit

- Print the commit subject + sha.
- If +pr-flow is installed and the user said "ship this" or "open a PR," suggest invoking the `open-pr` skill next.
